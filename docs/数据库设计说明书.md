参赛队伍：云穗智擎（山东建筑大学 计算机与人工智能学院）　队长：张衡　指导教师：刘新锋

## 一 设计目标

本系统的数据存储分为**数据湖**与**业务库**两部分，职责严格分离，这是大数据赛道要求"不得因数据规模小而使用非大数据技术"的工程落点。

| | 数据湖 | 业务库 |
| --- | --- | --- |
| 承载内容 | 百万级原始观测明细与分层加工结果 | 分析产出结果与业务操作记录 |
| 存储形态 | 分区文件（gzip CSV / Parquet + Snappy） | PostgreSQL 16（本地可降级 SQLite） |
| 计算引擎 | Apache Spark（可选 Hive Metastore 注册外部表） | SQLAlchemy ORM |
| 规模 | 1,591,545 条明细 | 万级 |
| 访问方 | 离线批处理作业 | 在线 API |

**明细数据不入业务库，业务操作记录不参与明细计算**，两者的唯一耦合点是 ADS 结果表的回流。

本章第二至第六节描述业务库设计，第七节描述数据湖分层设计。

业务库设计遵循"业务对象独立建表、外键关联、时间字段可追溯"的原则，表结构由 SQLAlchemy 模型统一维护，避免本地和容器环境出现字段漂移。

## 二 实体关系

`crops` 与 `farms` 为作物和地块基础关系；`farms` 向下关联天气、传感器、病虫害、产量、风险、预警和巡检记录。`alerts` 与 `inspection_tasks` 通过可选外键形成预警到任务的处置链路。`model_metrics` 保存训练评估结果，`knowledge_docs` 保存本地知识库索引。

## 三 核心表设计

| 表名 | 作用 | 关键字段 |
| --- | --- | --- |
| users | 登录用户和角色 | id、username、password_hash、role、display_name、organization |
| crops | 作物与适宜温度 | id、name、variety、growth_days、optimal_temp_min、optimal_temp_max |
| farms | 农田地块 | id、name、town、crop_id、area_mu、lat、lng、polygon_json、soil_type、irrigation_level、current_risk_score、risk_level |
| weather_records | 天气观测 | id、farm_id、town、record_date、temperature、humidity、rainfall、wind_speed、sunshine_hours、weather_type |
| sensor_records | 物联网传感器 | id、farm_id、recorded_at、soil_moisture、soil_temperature、ph、light_intensity、nitrogen、phosphorus、potassium、anomaly_flag |
| pest_disease_reports | 病虫害上报 | id、farm_id、crop_id、report_date、disease_name、severity、affected_area_mu、confidence、source、status、treatment_suggestion |
| yield_records | 历史与预测产量 | id、farm_id、crop_id、year、season、yield_kg_per_mu、predicted_yield_kg_per_mu、loss_rate |
| risk_predictions | 风险预测快照 | id、farm_id、prediction_date、risk_score、risk_level、top_factors、model_version |
| alerts | 预警事件 | id、farm_id、title、risk_level、trigger_reason、status、owner、suggestion、created_at、updated_at |
| inspection_tasks | 巡检任务 | id、farm_id、alert_id、title、priority、assignee、due_date、status、description、record、created_at、updated_at |

| knowledge_docs | 知识库文档 | id、source、title、content、indexed_at |

## 四 约束和索引

1. `users.username`、`crops.name` 和 `knowledge_docs.source` 设置唯一约束。
2. 地块名称、乡镇、风险等级和时间字段建立索引，服务地图筛选、趋势查询和预警列表。
3. 所有业务表使用整数主键；时间序列表保留日期或时间字段，便于按窗口查询。
4. `polygon_json` 保存演示用 GeoJSON 坐标，真实部署时可替换为 PostGIS 几何字段。
5. `top_factors` 以 JSON 字符串保存，兼顾 SQLite 和 PostgreSQL 的兼容性；升级到生产环境可迁移为 JSONB。

## 五 数据生命周期

原始观测数据进入数据湖 ODS 层（`data/lake/ods/`），经 Spark 清洗加工后依次落 DWD、DWS、ADS，ADS 结果回流业务库。模型训练数据取自 DWS 宽表并保留数据集版本，模型结果写入 `model_metrics` 与 `risk_predictions`。报告文件写入 `data/generated/reports`，文件名包含生成时间与报告编号。真实数据接入时应增加数据来源、授权范围与脱敏记录。

## 七 数据湖分层设计

### 1 层次与表

| 层 | 表 | 粒度 | 记录数 | 格式 |
| --- | --- | --- | --- | --- |
| ODS | `ods_sensor_raw` | 地块 × 终端 × 采集时点 | 1,405,790 | gzip CSV，`dt=YYYY-MM` 分区 |
| ODS | `ods_weather_raw` | 乡镇 × 小时 | 105,422 | 同上 |
| ODS | `ods_pest_scout_raw` | 单次踏查 | 65,890 | 同上 |
| ODS | `ods_yield_plot_raw` | 地块 × 年 × 季 × 小区 | 14,443 | 同上 |
| DWD | `dwd_sensor` / `dwd_weather` / `dwd_pest_scout` / `dwd_yield_plot` | 同 ODS | 合计 1,583,486 | Parquet + Snappy，`dt` 分区 |
| DWS | `dws_farm_daily` | 地块 × 日 | 58,400 | Parquet + Snappy，`dt` 分区 |
| ADS | 6 张结果表 | 聚合粒度 | 数十行 | JSON + CSV |

完整字段定义与注释见 `batch_jobs/spark_jobs/hive_ddl.sql`，该脚本可在具备 Hive Metastore 的环境中将四层注册为外部表（`EXTERNAL`，删表不删数据），使 Spark SQL、Hive CLI 与 BI 工具共用同一套口径。

### 2 分区与存储选型

- 按 `dt=YYYY-MM` 月分区，再按乡镇编码分文件，Spark 读取时可做分区裁剪，避免全量扫描。
- ODS 保留文本格式，贴近真实采集落地形态并保留脏数据；DWD 起转列式 Parquet + Snappy，兼顾压缩率与列裁剪性能。
- 明细层 438 个分区文件，gzip 后 39.0 MB。

### 3 与业务库的回流关系

Spark 产出的 ADS 结果表回流业务库，对应关系为：

| ADS 结果表 | 业务库消费方 |
| --- | --- |
| `ads_town_risk_ranking` | 驾驶舱乡镇排名接口 |
| `ads_crop_risk_distribution` | 驾驶舱作物结构接口 |
| `ads_risk_trend_30d` | 驾驶舱趋势接口 |
| `ads_inspection_priority` | `risk_predictions` 与巡检派单 |
| `ads_material_dispatch` | `/api/workflows/daily-dispatch` 调度建议 |
| `ads_yield_summary` | 产量预测页基线 |

回流为单向覆盖写：业务库中的分析类字段由 ETL 刷新，用户操作类字段（预警状态、巡检记录、处置反馈）由 API 写入，两类字段不重叠。

## 六 安全设计

密码只保存哈希值；JWT 密钥和外部服务 Key 通过环境变量注入；数据库连接信息不写入前端。日志记录请求编号、路径、状态和耗时，不记录密码、Token、图片原文和知识库密钥。合作社用户正式上线时应增加组织和地块授权关联，限制跨组织查询。
