## 一、问题定义

县域农业的病虫害防控长期依赖农技员经验与人工上报，存在四个结构性问题：

1. **发现滞后**。病虫害从田间出现到逐级上报往往数天，错过最佳防治窗口。
2. **数据分散且不可用**。气象站、物联网终端、农技站踏查、统计测产各成孤岛，格式与时间口径不一，采集端丢包、重传、故障读数普遍存在，无法直接用于分析。
3. **研判缺乏量化依据**。风险高低靠经验描述，无法排序，也无法回答"为什么这块地风险高"。
4. **资源调度无据可依**。植保无人机、农技员与药剂的投放靠平均分配，高风险区与投入不匹配。

本项目以山东省济宁市鱼台县为示范县域，建设一套从多源农情数据到防控决策的县域农业大数据与人工智能行业应用平台，把上述四个问题转化为可度量、可复核、可调度的数据问题。

## 二、用户角色与使用目标

| 角色 | 关注点 | 从系统获得 |
| --- | --- | --- |
| 县域农业主管部门 | 全县风险态势、乡镇排名、资源投放 | 驾驶舱指标、乡镇风险排名、农资与人机调度建议、农情日报 |
| 农技站 / 农技专家 | 具体地块的风险成因与处置 | 风险因子分解、病虫害识别结果与复核标记、巡检任务清单 |
| 合作社 / 种植大户 | 自有地块状况与待办 | 地块风险画像、图片上报与识别、巡检任务反馈 |

## 三、总体技术方案

系统由三条链路组成，离线分析链路是主线。

```
          [气象站] [物联网终端] [农技踏查] [测产记录] [叶片图像]
                              |
                     ODS 贴源层（分区 gzip CSV，159 万条明细）
                              |  Spark：去重 / 值域过滤 / 缺失回填 / 时间口径统一 / 质量打标
                     DWD 明细清洗层（Parquet + Snappy，按月分区）
                              |  Spark：乡镇-日、地块-日两级汇聚，14 日滚动窗口特征
                     DWS 风险特征宽表（地块 × 日，58,400 行）
                              |  Spark SQL：风险评分、分级、排名、归因、资源测算
                     ADS 应用层（6 张结果表，JSON / CSV）
                              |
            业务库（PostgreSQL）  →  FastAPI  →  Next.js 驾驶舱 / 地图 / 预警 / 巡检 / 报告
                              ↑
                   在线模型：病虫害检测、风险评分、产量预测、异常检测、RAG 问答
```

三条链路的分工：

- **离线分析链路（Spark）**：承担全部大体量数据的清洗、关联、特征加工与聚合，产出应用层结果。
- **在线服务链路（FastAPI + Next.js）**：只读应用层结果与业务操作记录，保证页面秒级响应。
- **模型链路（backend/ml、backend/rag）**：提供图像检测、风险评分、产量预测、异常检测与检索增强问答，结果回写业务库并纳入同一套可解释性口径。

## 四、大数据处理链路（核心）

### 1. ODS 贴源层

由 `scripts/generate_bigdata_layer.py` 生成，固定种子 `SEED = 20260506`，双核环境实测 35 秒完成。落盘路径 `data/lake/ods/<表名>/dt=YYYY-MM/part-<乡镇编码>.csv.gz`，共 438 个分区文件、39.0 MB。

| 表名 | 粒度 | 记录数 |
| --- | --- | --- |
| `ods_sensor_raw` | 地块 × 2 终端 × 730 天 × 每日 12 次 | 1,405,790 |
| `ods_weather_raw` | 乡镇 × 730 天 × 逐小时 | 105,422 |
| `ods_pest_scout_raw` | 每日约 90 条踏查 | 65,890 |
| `ods_yield_plot_raw` | 地块 × 年 × 两季 × 30 小区 | 14,443 |
| 合计 | | **1,591,545** |

生成时按 0.8% / 0.3% / 0.2% 的比例注入字段缺失、整行重复与越界读数，模拟采集端丢包、重传与传感器故障，使清洗环节有真实处理对象。

### 2. DWD 明细清洗层

Spark 作业 `batch_jobs/spark_jobs/agri_etl_pipeline.py` 执行五类清洗：

1. **去重**：按 `record_id` 做 `dropDuplicates`，剔除重传重复 4,727 条。
2. **值域过滤**：按各观测量的物理合法区间（如土壤含水量 0.02—0.98、气温 -35—50℃）判定故障读数，越界置空并打 `is_outlier` 标记。
3. **缺失处理**：分级策略——墒情等关键特征缺失则整行剔除；气温、湿度等可插补字段按乡镇窗口均值回填，避免整行丢弃造成时序断点。
4. **时间口径统一**：统一解析为 timestamp，派生 `stat_date` 与 `dt` 分区字段，解决各源时间格式不一致的问题。
5. **质量度量**：逐表统计原始量、去重量、无效量与保留量，写入 `ads_data_quality.json`。

清洗结果：保留 1,583,486 条，剔除 8,059 条，整体有效率 99.49%。DWD 层以 Parquet + Snappy 按 `dt` 分区存储，列式压缩与分区裁剪使下游聚合只扫描必要数据。

### 3. DWS 风险特征宽表

三路汇聚后关联为地块-日粒度宽表，共 58,400 行（80 地块 × 730 天）：

- **气象日聚合**（乡镇 × 日）：日均温、日最高温、日均湿、日累计降水、日均风速、相对湿度≥85% 的小时数。
- **传感器日聚合**（地块 × 日）：日均墒情、墒情日内标准差、土温、pH、氮钾均值、有效采集条数、异常读数条数。
- **踏查日聚合**（地块 × 日）：平均病株率、最高病株率、受害面积、踏查次数。
- **时序窗口特征**：用 Spark 窗口函数 `rangeBetween(-14天, -1天)` 计算近 14 日历史病害压力滚动均值，刻画病害的累积效应，这是单点观测无法表达的。

### 4. 风险评分与分级

综合风险评分为五项因子的加权和再乘以作物易感性系数，满分 100：

| 因子 | 计算口径 | 满分 | 农技依据 |
| --- | --- | --- | --- |
| 空气湿度 | 日均湿度超过 60% 的部分线性映射 | 34 | 高湿是绝大多数真菌性病害的首要诱因 |
| 降雨量 | 日累计降水线性映射，30mm 封顶 | 18 | 降雨造成叶面结露与孢子飞溅传播 |
| 土壤墒情 | 日均含水量超过 0.32 的部分线性映射 | 16 | 过湿导致根系缺氧、抗性下降 |
| 历史病害 | 近 14 日病株率滚动均值线性映射 | 22 | 病原基数决定再侵染强度 |
| 积温条件 | 日均温超过 18℃ 的部分线性映射 | 10 | 温度决定病原发育速率 |

作物易感性系数：番茄 1.20、水稻 1.15、黄瓜 1.10、小麦 0.95、玉米 0.90。

**分级阈值按分布标定而非拍脑袋**：对 2024-09 至 2026-08 全量 58,400 条地块-日记录的风险评分做分位数统计，取高风险阈值 52（约 P96）、中风险阈值 36（约 P80），再对照主汛期 6—9 月校核，使汛期高风险地块占比约 10.5%、中风险约 38.4%，与县域植保的资源承载能力相匹配。阈值定义集中在 `RISK_HIGH` / `RISK_MID` 两个常量，调整即可整链生效。

同时输出**主导风险因子**：取五项分值中的最大者，回答"这块地为什么风险高"，供农技员现场复核。

### 5. ADS 应用层

Spark SQL 产出 6 张结果表，直接供 API 与前端消费：

| 结果表 | 内容 | 业务用途 |
| --- | --- | --- |
| `ads_town_risk_ranking` | 乡镇平均风险、高风险地块数、受害面积 | 驾驶舱乡镇排名 |
| `ads_crop_risk_distribution` | 作物 × 风险等级的地块分布 | 作物结构风险分析 |
| `ads_risk_trend_30d` | 近 30 日全县风险走势与高风险地块数 | 趋势研判 |
| `ads_yield_summary` | 作物 × 年份的平均亩产与损失率 | 产量与减产归因 |
| `ads_inspection_priority` | 风险 Top 30 地块及主导因子 | 巡检排序与派单 |
| `ads_material_dispatch` | 各乡镇无人机架次、农技员人数、药剂用量 | 农资与人机调度 |

以最新统计日 2026-08-31 为例，全县 80 个地块中高风险 14 个、中风险 36 个、低风险 30 个；高风险集中在水稻（10 个）与番茄（4 个），与两者易感性高、8 月底处于稻瘟病与纹枯病高发期的农技规律一致；受害面积最大的清河镇测算需无人机 5 架次、农技员 3 人、药剂 178.4 kg。

### 6. Hive 数仓与运行环境

`batch_jobs/spark_jobs/hive_ddl.sql` 提供 ODS / DWD / DWS / ADS 四层外部表建表脚本，可在具备 Hive Metastore 的环境注册，使 Spark SQL、Hive CLI 与 BI 工具共用同一套口径。

运行环境通过 `docker-compose.bigdata.yml` 提供，包含 Spark Master、Worker 与作业提交入口，并提供 `spark-local` 单容器模式供评委一键复现，规避 Windows 下 Hadoop winutils 的环境依赖。作业结束写出 `data/lake/_run_report.json`，记录各层行数、清洗剔除量与阶段耗时。

### 7. 口径一致性保障

`batch_jobs/pandas_jobs/ads_reference_job.py` 是同一套清洗规则与评分公式的 pandas 参考实现，读同一份 ODS 数据。`scripts/compare_ads_outputs.py` 逐表逐字段比对 Spark 产出与参考产出，容差 0.02，任何一侧改动口径都会立即暴露。这使分析结果可复核，而不是一次性跑数。

## 五、在线业务系统

### 1. 架构

前端 Next.js 16 + React + TypeScript + Tailwind CSS，图表用 Recharts，地图用 Leaflet；后端 FastAPI + SQLAlchemy，JWT 认证，自动请求日志与统一错误响应，提供 Swagger 文档；数据库 Docker 环境用 PostgreSQL 16，本地可降级 SQLite。

### 2. 功能模块

- **农情驾驶舱**：核心指标、风险趋势、作物结构、乡镇排名、最新预警。
- **县域风险地图**：地块 polygon 按风险等级着色，支持按乡镇、作物、等级筛选，点击查看地块画像与主导风险因子。
- **病虫害识别**：上传叶片图像，返回病害名称、置信度、严重度、检测框、防治建议与人工复核标记。
- **风险与产量预测**：风险评分曲线、产量预测曲线、误差指标与特征贡献。
- **预警与巡检闭环**：风险越阈生成预警，预警一键生成巡检任务，现场反馈回写。
- **AI 农技助手**：RAGFlow 远程优先、本地 TF-IDF 降级，回答带引用来源并标注实际调用模式。
- **数据导入导出与日报**：CSV 导入导出，生成 Markdown / HTML 农情日报。

### 3. 主要接口

认证 `/api/auth/*`；驾驶舱 `/api/dashboard/*`；地块 `/api/farms/*`；识别 `/api/disease/predict`；预测 `/api/predictions/*` 与 `/api/model/metrics`；预警 `/api/alerts/*`；巡检 `/api/inspection-tasks/*`；助手 `/api/assistant/*`；数据 `/api/data/*`；报告 `/api/reports/*`；调度工作流 `/api/workflows/daily-dispatch`。

## 六、AI 模型设计

### 1. 病虫害图像检测

`backend/ml/disease_classifier.py` 定义统一接口 `predict(image_bytes)`，返回 `disease_name`、`confidence`、`severity`、`suggestion`、`need_review`、`explainability`。`backend/ml/yolo_disease_classifier.py` 为 YOLO 检测适配器，返回结构与基线一致。模型由 `MOCK_DISEASE_MODEL`、`DISEASE_MODEL_PROVIDER`、`PEST_YOLO_MODEL_PATH` 三个环境变量切换，替换真实权重时保持契约不变。

训练数据与指标见 `docs/数据集说明.md` 第七节。**所有指标均为公开数据集评测结果，不代表山东本地田间准确率**，这一边界在 PPT、视频与答辩中必须明确说明。

### 2. 风险评分模型

`backend/ml/risk_model.py` 使用 RandomForestRegressor，输入 DWS 宽表的气象、墒情、历史病害、作物与地块特征，输出风险评分、等级与特征贡献，指标含 MAE、RMSE、R²。规则评分与模型评分互为交叉验证：规则评分可解释、可审计，模型评分捕捉非线性交互，两者差异大的地块进入人工复核队列。

### 3. 产量预测模型

`backend/ml/yield_forecast.py` 使用 RandomForestRegressor，输入历史测产、风险累积、气象与地块特征，输出未来产量曲线、误差指标与主要影响因素。

### 4. 异常检测

`backend/ml/anomaly_detector.py` 使用 IsolationForest 识别墒情、pH、光照与养分异常，与 DWD 层的规则化 `is_outlier` 标记形成互补：规则捕捉硬故障，模型捕捉分布漂移。

### 5. RAG 农技问答

`backend/rag/` 优先调用 RAGFlow 远程知识库并解析文档引用，结合当前高风险地块与最新天气组织回答；远程超时或不可用时自动降级到 `knowledge_base/*.md` 的 TF-IDF 检索，接口用 `mode`、`provider`、`warning` 标识实际执行路径，避免把降级结果误认为远程结果。

## 七、测试方案

1. **后端接口测试**：pytest + TestClient，覆盖健康检查、登录、驾驶舱摘要与病虫害识别。
2. **大数据链路测试**：造数脚本对记录总数做断言（不足 100 万条直接失败退出）；`compare_ads_outputs.py` 做 Spark 与参考实现的口径一致性比对。
3. **数据质量测试**：清洗前后各表行数与剔除量写入 `ads_data_quality.json`，可逐表核对。
4. **可复现性测试**：固定种子两次生成，`ods_manifest.json` 中的行数、文件数与体积应完全一致。
5. **前端构建与页面走查**：`npm run lint`、`npm run build`，逐页检查加载、错误与空状态。

## 八、部署方案

在线系统用 `docker-compose.yml` 编排 PostgreSQL、FastAPI 与 Next.js；大数据环境用 `docker-compose.bigdata.yml` 单独编排 Spark，两者互不影响，可分别启停。服务器部署使用 `docker-compose.server.yml` 覆盖端口与数据目录。生产部署建议增加 Nginx、HTTPS、日志采集、数据库备份与权限分级。

## 九、风险与边界

| 风险 | 应对 |
| --- | --- |
| 仿真数据与真实数据分布存在差异 | 明细层表结构即真实数据接入契约，替换数据源后下游无需改动；文档明确标注数据性质 |
| 公开数据集指标不等于本地田间表现 | 所有材料统一标注边界；后续采集本地样本重新训练或微调 |
| 规则阈值可能随年份气候变化漂移 | 阈值由分位数标定并集中为常量，可按新一年数据重新标定 |
| 地图瓦片依赖外部网络 | 地块 polygon 与风险着色不依赖瓦片服务；答辩准备离线截图或本地底图 |
| RAGFlow 远程响应偏慢 | 已实现超时自动降级本地知识库，接口标注实际模式 |

## 十、创新点

1. **真正的数仓分层落地**：不是把 Spark 当作可选扩展，而是让 ODS→DWD→DWS→ADS 成为唯一的数据加工路径，业务库只消费产出。
2. **可度量的数据治理**：刻意注入并度量脏数据，用 99.49% 的有效率与逐表剔除量把"数据清洗"变成可核对的事实。
3. **阈值按分布标定**：风险分级阈值来自全量分位数统计并经汛期校核，可解释、可复标定，而非经验常数。
4. **风险归因到因子**：输出主导风险因子而非仅给分数，把模型结论转化为农技员能执行的动作。
5. **双实现口径互校**：Spark 主链路与 pandas 参考实现逐字段比对，保证分析结果可复核。
6. **分析结果直达调度**：从风险评分一路推到无人机架次、农技员人数与药剂用量，闭合"分析—决策—执行"。

## 十一、可行性

技术栈全部为成熟开源组件，依赖清晰、部署可控。县域农业的数据对象稳定，地块确权、气象站、物联网平台、农技踏查与测产记录在多数县域数字农业系统中均已存在，可按明细层契约直接接入。平台具备从竞赛演示向真实试点扩展的可行性。
