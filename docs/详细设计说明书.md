## 〇 大数据 ETL 主链路设计

离线分析由 `batch_jobs/spark_jobs/agri_etl_pipeline.py` 实现，是平台唯一的明细数据加工路径。

### 1 分层与存储格式

| 层 | 路径 | 格式 | 分区 | 说明 |
| --- | --- | --- | --- | --- |
| ODS | `data/lake/ods/<表>/` | gzip CSV | `dt=YYYY-MM` + 乡镇分文件 | 贴源不加工，保留原始脏数据 |
| DWD | `data/lake/dwd/<表>/` | Parquet + Snappy | `dt` | 去重、值域过滤、缺失处理、时间口径统一后的明细 |
| DWS | `data/lake/dws/dws_farm_daily/` | Parquet + Snappy | `dt` | 地块-日风险特征宽表 |
| ADS | `data/lake/ads/` | JSON + CSV | 无 | 六张应用结果表，供 API 直读 |

选择 CSV 作为贴源格式是为了贴近真实采集落地形态并保留脏数据；从 DWD 起转为列式 Parquet，配合分区裁剪，使下游聚合只扫描必要列与必要分区。

### 2 清洗规则

| 规则 | 实现 | 处理对象 |
| --- | --- | --- |
| 去重 | 按 `record_id` 执行 `dropDuplicates` | 采集端重传、断网补传造成的整行重复 |
| 值域过滤 | 按 `VALID_RANGES` 常量判定物理合法区间，越界置空并打 `is_outlier` | 传感器故障输出的 -999 / 9999 |
| 缺失分级 | 关键字段（墒情、时间、地块）缺失整行剔除；可插补字段按乡镇窗口均值回填 | 丢包与漏填 |
| 时间口径 | 统一解析为 timestamp，派生 `stat_date` 与 `dt` | 各源时间格式不一致 |
| 质量度量 | 逐表记录 raw / duplicates_removed / invalid_removed / kept | 数据治理举证 |

实测：原始 1,591,545 条，去重剔除 4,727 条，越界与缺失剔除 3,332 条，保留 1,583,486 条，有效率 99.49%。

### 3 DWS 宽表构建

三路并行汇聚后关联：

- 气象日聚合（乡镇 × 日）：`avg_temp`、`max_temp`、`avg_humidity`、`rainfall_mm`、`avg_wind`、`high_humid_hours`（相对湿度 ≥85% 的小时数）。
- 传感器日聚合（地块 × 日）：`avg_soil_moisture`、`std_soil_moisture`、`avg_soil_temp`、`avg_soil_ph`、`avg_nitrogen`、`avg_potassium`、`reading_cnt`、`outlier_cnt`。
- 踏查日聚合（地块 × 日）：`avg_incidence`、`max_incidence`、`affected_mu`、`scout_cnt`。

关联时对作物易感性维表使用 `broadcast` 提示，避免小表参与 shuffle。随后用窗口函数

```python
Window.partitionBy("farm_id").orderBy(col("stat_date").cast("long")).rangeBetween(-14*86400, -86400)
```

计算 `hist_incidence_14d`——近 14 日（不含当日）历史病害压力滚动均值，刻画病原基数的累积效应。输出 58,400 行（80 地块 × 730 天）。

### 4 风险评分与分级

```
risk_score = min( (humid_score + rain_score + moist_score + hist_score + temp_score)
                  × susceptibility , 100 )
```

| 因子 | 公式 | 上限 |
| --- | --- | --- |
| `humid_score` | clip((avg_humidity − 60) / 35 × 34, 0, 34) | 34 |
| `rain_score` | min(rainfall_mm / 30 × 18, 18) | 18 |
| `moist_score` | clip((avg_soil_moisture − 0.32) / 0.35 × 16, 0, 16) | 16 |
| `hist_score` | min(hist_incidence_14d / 20 × 22, 22) | 22 |
| `temp_score` | clip((avg_temp − 18) / 14 × 10, 0, 10) | 10 |

易感性系数：番茄 1.20、水稻 1.15、黄瓜 1.10、小麦 0.95、玉米 0.90。

分级阈值 `RISK_HIGH = 52`、`RISK_MID = 36`，来自对全量 58,400 条记录风险分数的分位数统计（约 P96 与 P80），并以主汛期 6—9 月的高风险占比约 10.5% 做校核。阈值集中为两个模块级常量，Spark 与参考实现共享，修改即整链生效。

`top_factor` 取五项分值中的最大者，用 `array_sort` + `element_at(-1)` 实现，输出可读的因子名称，供农技员判断处置方向。

### 5 ADS 结果表

| 表 | 口径 |
| --- | --- |
| `ads_town_risk_ranking` | 最新统计日按乡镇聚合平均风险、高风险地块数、地块数、受害面积，按风险降序 |
| `ads_crop_risk_distribution` | 最新统计日按作物 × 风险等级统计地块数与平均风险 |
| `ads_risk_trend_30d` | 近 30 日逐日全县平均风险与高风险地块数 |
| `ads_yield_summary` | 按作物 × 年份统计平均亩产、平均损失率、小区样本数 |
| `ads_inspection_priority` | 最新统计日风险 Top 30 地块及主导因子与优先级 |
| `ads_material_dispatch` | 按乡镇推算无人机架次（受害面积 ÷ 300）、农技员人数（÷ 500）、药剂用量（× 0.12 kg/亩） |

### 6 运行与举证

作业结束写出 `data/lake/_run_report.json`，包含 Spark 版本、master 地址、并行度、各层行数、逐表数据质量与 ODS→DWD、DWD→DWS、DWS→ADS 三阶段耗时，可直接作为答辩证据。

## 二 模型设计

### 1 风险评分

系统同时保留两套风险评分，互为交叉验证：

1. **规则评分（主口径）**：见本文第〇章第 4 节，公式透明、阈值来自分位数标定，可审计、可向农技人员解释，是地图着色、预警触发与巡检排序的依据。
2. **模型评分（辅助）**：`backend/ml/risk_model.py` 以 DWS 宽表字段为输入训练 RandomForestRegressor，输出 0—100 风险分数与特征重要性，用于捕捉规则公式未刻画的非线性交互，指标含 MAE、RMSE、R²。

两者差异超过设定容忍度的地块进入人工复核队列，既避免纯规则的僵化，也避免纯模型的不可解释。

### 2 产量预测

将历史产量、天气统计、风险分数、作物类别和地块属性编码后输入 RandomForestRegressor，输出未来产量和预测区间。训练阶段计算 MAE、RMSE 和 R2，并将指标写入 `model_metrics`。

### 3 异常检测

对土壤墒情、温度、pH、光照和氮磷钾等数值做标准化，使用 IsolationForest 输出异常点。异常记录保留原始时间、地块和异常原因，供管理者复核。

### 4 病虫害识别

`backend/ml/disease_classifier.py` 保持统一 `predict(image_bytes)` 接口。当前工程包含轻量分类接口、PlantDoc YOLO 权重调用接口和 Mock fallback。真实部署时可替换为经过本地样本验证的 YOLO 或 PyTorch 模型，并保留置信度阈值和人工复核策略。

## 三 RAG 助手设计

本地检索器读取 `knowledge_base/*.md`，使用 TF-IDF 计算问题与段落相似度，返回引用来源。RAGFlow 客户端先检查数据集和聊天助手状态，再向远程会话发送问题；响应中提取回答和文档引用。业务层将高风险地块与近期天气摘要作为系统上下文附加到答案末尾，回答中明确区分知识库建议和系统实时数据。

## 四 前端设计

前端通过 `src/lib/api.ts` 统一请求，自动携带 JWT 并在 401 时回到登录页。页面采用 App Shell、Sidebar、Topbar 和内容区结构，图表采用 Recharts，地图采用 Leaflet。表格页面提供搜索、筛选、分页或状态标签；识别页处理拖拽上传、图片预览、进度状态、结果和复核提示；助手页面固定对话区域高度，避免连续提问造成页面无限增长。

## 五 批处理与口径校验设计

离线批处理的主实现是第〇章的 Spark ETL 主链路。除此之外还有两个配套件：

1. `batch_jobs/pandas_jobs/ads_reference_job.py`——同口径的 pandas 参考实现，读同一份 ODS 数据、用同一套清洗规则与评分公式，作为回归基线，在没有 Spark 环境时也能产出可比对的结果。
2. `scripts/compare_ads_outputs.py`——逐表逐字段比对 Spark 产出与参考产出，数值容差 0.02（覆盖两侧 round 实现差异），字符串严格相等。行数不一致、字段缺失或取值超差都会打印明细并以退出码 1 失败。

该设计使"分析结果正确"成为可自动验证的命题，而不是依赖人工肉眼核对。

`batch_jobs/pandas_jobs/risk_aggregation_job.py` 为早期版本的业务库轻量聚合，保留用于业务库侧的小规模统计，不参与明细层计算。

## 六 日志与故障处理

请求中间件生成 request_id 并记录方法、路径、状态码和耗时。RAGFlow API Key 在异常信息中脱敏，上传图片只保存在临时内存中。外部服务超时后在限定窗口内降级本地能力，模型文件缺失时返回明确提示。数据库写入失败时回滚事务，避免生成半条预警或任务记录。

## 七 测试设计

测试分四层：

1. **数据层**：造数脚本对明细总量做断言，不足 100 万条即以非零退出码失败；`ods_manifest.json` 记录行数、文件数与体积，用于复现性核对。
2. **分析层**：Spark 作业输出各层行数与数据质量报告；`compare_ads_outputs.py` 校验 Spark 与参考实现的口径一致性。
3. **接口层**：pytest + FastAPI TestClient 覆盖健康检查、登录、驾驶舱与识别接口；模型训练脚本检查模型文件与指标文件。
4. **前端与部署**：`npm run lint`、`npm run build` 与核心页面走查；在目标机器执行容器启动、数据初始化、接口访问与浏览器端到端演示。
